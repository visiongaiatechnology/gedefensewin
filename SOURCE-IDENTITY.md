# SOURCE IDENTITY — GeDefense Windows

**Status:** authoritative for this source tree.
**Scope:** every build, release and audit decision that needs a version identity.

## 1. Why this document exists

The audited workspace directory is named `5.2.0_Source`, while the files inside
it declare version `6.1.0` (`VERSION`, `internal/product/version.go`,
`CHANGELOG.md`). A directory name is a filesystem label chosen by the workspace
owner and is **not** a version. Without a recorded rule this difference is
indistinguishable from a real release-identity conflict (`FIND-WIN-022` /
`VGT-055`).

## 2. Authoritative identity chain

The version identity of this tree is defined **only** by the following files, in
this order:

| Rank | File | Meaning |
|---|---|---|
| 1 | `VERSION` | The version every build and installer must use. |
| 2 | `src/GeDefense/windows/internal/product/version.go` | The version compiled into the binaries. |
| 3 | `CHANGELOG.md` | The newest `## [x.y.z]` heading documents the same version. |
| 4 | `SOURCE-MANIFEST.sha256` | Integrity manifest regenerated from this tree at build time. |

Rules:

- Ranks 1–3 must be equal. `internal/product` enforces this in
  `identity_test.go`; an unequal pair fails `go test ./internal/product/...`.
- `SOURCE-MANIFEST.sha256` is generated by `build/Build-SourceRelease.ps1` and is
  never hand-edited. A stale manifest is a build failure, not a documentation
  problem.
- The directory name (`5.2.0_Source`) carries **no** version meaning. Historical
  workspace labels stay untouched because build scripts, operator runbooks and
  audit references point at them.

## 3. Release artifacts

Release artifact names derive from `VERSION` (`GeDefense-Setup-x64-v<version>.exe`,
sidecar, SBOM, provenance, source archive). An artifact whose embedded version
does not equal `VERSION` must not be published. `release/` must contain exactly
the registered asset set for the current version; stale artifacts from other
versions are removed before a release build, never shipped silently.

## 4. Conflict procedure

If `VERSION`, `product.Version` and the newest `CHANGELOG.md` heading disagree:

1. Stop the release (fail-closed). Do not pick a number by intuition.
2. Record the conflict here with file, line, observed value and timestamp.
3. Decide the intended release version in the changelog entry, then update all
   three files in one change and regenerate the manifest.
